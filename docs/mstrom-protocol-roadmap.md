## 第二阶段结论速览(20 路并行研究,详见 docs/mstrom-card-parsing-blueprint.md)

- **载荷 = protobuf 线格式**(type2 帧 96.9% 完整消费);「TLV 标签」是键字节巧合伪影;type3 状态帧=自定义二进制体(11B头+f64+N×12B 市场记录)
- **帧头修正**:[u16 type][u16 x16][u32 totalLength][u32 rawHeaderSeq],无校验字段；当前解析器硬校验 type 白名单、totalLength 自洽与桌台键识别，tick/序号单调性只属于证据层观察
- **换靴最终判据（2026-08-24）**:只接受 `x16=0x1016` 的 `GameSnapshot.gmstatus=11`，以及协议常量 `x16=0x001c` (`RESET_SHOECODE_R`)；type3 金额/市场状态永不自动升级为 `physical-shoe`
- **已破译**:f4/f5=庄/闲分、f3=阶段码(1下注/2停注/0开牌)、f10[0]=结果码(01庄/02闲/03和)、珠盘 varint 记录=赢家+点数(g0/g1 位域)、市场 ID 14 个、金额=IEEE754 BE double
- **跨游戏牌编码实证**:卡字节=suit<<4|rank(suit 0-3/rank 1-13),龙虎 18/18 吻合;BJ 暗牌=ff01
- **BAC 牌面主嫌疑**:x1016.f10 尾部(开牌专用,97% deal 门控)——未破译,判别实验 P0-0/P0-1 见蓝图 §5
- GT 样本局已在 app-console.log 精确锚定(SL/SZ verified);G串尾缀=f2−每桌常数(可打绝对局号);结算滞后一局,对齐须用 f3=0 结算簇

## 已确认的协议结构(第一阶段记录,⚠️ 多处已被第二阶段修正,保留作历史)

### 帧结构(❌ 第一阶段记录已推翻)
```
旧误读: [u16 类型][u16 长度][u32 序号][u16 校验][u16 0000]
正确值: [u16 type][u16 x16][u32 totalLength][u32 seq]
```
偏移 4 的四字节是**整帧总长度**，偏移 8 的四字节才是 `seq`；不存在旧记录所称的校验字段。type2 载荷使用 protobuf 线格式，不能继续按自定义 TLV 解释。
**已确认语义的标签**:0x0a=游戏类型("BAC"/"ROU")、0x12=局号串("GN0172682111W")、0x18=2字节值、0x41/0x42=状态哈希
**待确认**:其余 40+ 标签(牌面数据必是其中之一,需开牌瞬间定向对照)
完整枚举工具:scripts/temp-analyze19.cjs(通用 TLV 解析器 parseFrame)
游戏类型后缀:BAC 百家乐 | DT 龙虎 | BJ 廿一 | ZJH 炸金花 | SG 三公 | ROU 路子 | LBA/SHB/N/P/D 变体

### ✅ 换靴信号最终校准（2026-08-24）

站点主包已确认常量：

```text
GAME_SNAPSHOT_PROTO = 135190 (0x21016)，低 16 位映射为 type2 header x16=0x1016
RESET_SHOECODE_R    = 131100 (0x2001c)，低 16 位映射为 type2 header x16=0x001c
GameSnapshot.gmstatus === 11
  -> onShuffle()
  -> ACTION_GAME_SHUFFLE
```

生产规则：

1. `x16=0x1016 && protobuf field 3 (gmstatus) === 11`：确认物理新靴。
2. `x16=0x001c`：协议定义的显式重置响应，可确认物理新靴；当前七份实时日志尚无该帧样本。
3. 页面已解码的 `GameSnapshot.gmstatus=11`：作为 raw protocol 的同边界后备来源，使用 `game-snapshot:${roundId}` 与协议路径幂等。
4. type3 的 `statusLength`、`counterA`、累计金额、空市场连发只保留诊断价值，**永不**产生 `physical-shoe`。
5. `x1008` 简化广播常伴随洗牌，但 20 个真实边界中有 2 个先经过至少 3 条控制帧，因此它只能做旁证，不能作为固定窗口硬门控。

旧「字段8 长度骤降 + 计数器跳变」规则已被真实回放证伪：D056 普通局 BL→BM 的 45 帧可稳定触发旧规则，造成假换靴；D067 的真实换靴帧则早已到达 WS，但旧事件层和 runtime hook 同时过滤了 `gmstatus=11`，造成漏报。

### 桌台状态帧（type3：20 + 12N）
```
[u8 00][u16BE A][u16BE B][u16BE C][u32 00000000]
[f64BE totalAmount][u8 N][N×12B market]

market = [u16BE marketId][u16BE bettorCount][f64BE amount]
```
- 状态体长度恒为 `20 + 12*N`；每增加 12B 只表示新增一条市场记录。
- `0x0001`=庄、`0x0002`=闲、`0x0003`=和；其余 ID 为对子/龙宝等衍生市场。
- A/B/C、倒计时、累计金额和空市场形态只用于状态诊断，不能确认物理换靴。

### 广播序列串(G 串)
- 格式:G + 桌台码 + 26821x + 计数后缀(base36 递增)
- 每桌独立计数器,随广播递增;5 分钟内单桌可广播 9+ 次
- ✅ 与界面上的"游戏局号"(GD065268211OH 这类)是同一个东西(早期误判为不同)
- 广播计数器按局递增(极速桌约 55 秒/局),不同桌速率不同

### 界面"游戏局号"(✅ 已确认 = 广播串本身)
- 格式:G + 桌台码 + 日期段(26821 ≈ 当日日期)+ 平台位 + 局计数(1-2 字符 base36 递增)
- 整局生命周期不变;洗牌中出现占位局号;新靴第一局换新号
- ✅ 监听每桌最新广播串即可追踪"当前第几局";代码跳变 = 新的一局开始
