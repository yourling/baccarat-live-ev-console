## 二、资金安全

### 2.1 对子窗口校验被时钟偏差绕过 ★

`packages/orchestrator/src/betting-window.ts:18`

```diff
- return Math.abs(now - closesAtMs) > 60_000 ? closesAtMs - 10_000 : now;
+ return Math.abs(now - closesAtMs) > 60_000 ? closesAtMs : now;
```

旧写法在偏差 >60s 时返回 `closesAtMs - 10_000`，使剩余时间恒为 10000ms（≥3000ms 阈值），
**窗口校验永远通过** —— 恰好在时钟不可信、最需要这道闸的时候把它关掉了。
现在返回 `closesAtMs` 使剩余为 0，保守拒绝。

新增 `packages/orchestrator/test/betting-window.test.ts`（10 个用例，含超前/落后/容差/不越界）。

### 2.2 手工下注与关闭竞态

`apps/desktop/electron-src/service.ts`

**踩坑记录**：最初在外层包 `enqueueExecutionStateOperation`，导致死锁超时 ——
coordinator 的 `serialize` 选项已经走同一条队列，重复排队会自等待。

最终方案：
- `operationalWagerRuntimeBlockReason` 开头加 `if (this.closing) return 'console-closing'`
  （这道闸在**队列内部**，能挡住"排在 `close()` 之后才被调度"的下注）
- `executeOperationalWager` 保留开头的快速失败检查
- `finally` 里**重新读取** `this.browserBridge`，避免拿旧引用去关已拆除的桥

新增测试：`operational-wager-service.test.ts` 的 "refuses a manual wager once the console is closing"。

### 2.3 BG 真金通道补校验

- `apps/browser-extension-bg/bg-protocol.js` 的 `submit`：加回合一致性校验
  （`handId` 必须等于 `session.seqNoByTable[tableId]`，采到才拦）+ 桌台限注校验
- `apps/browser-extension-bg/bg-bet-runtime.js` 的 `precommitReason`：同样两项
- 新增 `session.tableLimitsByTable`（采集侧写入，未采集到则放行）

**遗留**：BG 扩展目前**没有采集桌台限注**，所以限注校验只在有数据时生效。
需要采集侧补上才会真正拦住超限金额。

### 2.4 RESERVED 预留泄漏

`packages/risk-execution/src/risk.ts` 新增：

```ts
escalateOverdueSettlements(maxAgeMs, now, reason, notBefore?): RiskReservation[]
```

把"有回执、超过 10 分钟未结算、且不是启动时从账本恢复"的 RESERVED 升级为 **UNKNOWN**。

关键设计取舍：**不释放敞口**（未知的钱不能当成没发生），只把状态变成显式可处置，
让它进入既有的 `unknown-execution` 告警与操作员勾销流程，而不是永久静默占满全局敞口与并发额度。

`notBefore = service.runtimeStartedAt` 用于放过启动恢复的历史敞口
（它们早已超出任何时间阈值，一升级就会把该桌直接阻断）。

新增 3 个测试覆盖升级、幂等、不自升级无回执预留、不碰启动恢复敞口。

### 8.1 `scheduleDemotedTableFeedStop` 可能关掉"新"连接（我引入的）

上一轮版本在队列里现场取 `this.liveFeeds.get(tableId)`，谁在就停谁。
但这个方法是在 live monitor 队列**内部**被同步调用的，真正停 feed 排在队列尾；
期间该桌完全可能被重新晋升并挂上**新的** feed —— 那时会把新连接关掉。

已改为排队前捕获 feed 引用，执行时比对 `!== demotedFeed` 就跳过，
与项目既有的 `stopLiveFeedForTransition` 的 `not-current` 约定一致。

### 8.2 ★ `settleHand` 不认新的 UNKNOWN reason（上一轮修复不完整）

上一轮的 `escalateOverdueSettlements` 把预留标成 `UNKNOWN / unsettled-past-timeout`，
但 `RiskManager.settleHand` 只把 `releaseReason === 'hand-settled-without-authoritative-outcome'`
的 UNKNOWN 纳入自动收敛。

后果：被超时升级的预留，**即使迟到的权威结算终于到达也无法自动结算**，
会永远卡在 UNKNOWN，必须操作员手工勾销 —— 等于把"可自愈"的情况变成了"必须人工"。

已抽出 `isSettleableUnknown(reason)`，把 `unsettled-past-timeout` 一并纳入；
回执不匹配那类"执行结果本身不可信"的 UNKNOWN 仍然拒绝自动收敛（这是刻意的）。
新增 2 个测试：迟到结算能收敛、不可信 UNKNOWN 仍不收敛。

### 8.3 `package-lock.json` 版本漂移（既有问题，已发生 10 次）

`package.json` 已到 1.0.10，lockfile 还停在 **1.0.1** —— 历次 bump 都没同步它。
`npm ci` 不会因此失败（实测 exit 0），但它会让人对"发布的是哪一版"失去判断，
且下次 `npm install` 会产生意外 diff。

- 已把 lockfile 的顶层 / `packages[""]` / `packages["apps/desktop"]` 三处同步到 1.0.11
- 新增 `scripts/check-version-sync.mjs`，一次性校验全部 6 个版本面
  （3 个原有 + lockfile 的 3 处），接入 `npm run build` 与 pre-commit
- 已验证：故意制造不一致时 exit 1，一致时 exit 0

### 8.4 行尾符被 `sed -i` 破坏（我自己造成的）

用 `sed -i` 改版本号与调试时，把 3 个原本 CRLF 的文件改写成了 LF：
`apps/desktop/electron-src/service.ts`、`apps/desktop/src/console-build-info.ts`、
`apps/desktop/test/console-build-info.test.ts`（同目录其它文件全是 CRLF）。

已全部转回 CRLF，并对我新建的文件（`.d.mts`、`betting-window.test.ts`、两份报告）统一为
项目规范 CRLF。复核扫描确认无其它意外 LF 文件。

保留 LF 的（**本来就该是**，不是我造成的）：`package.json` 系列（连 `packages/contracts`
在内的 10 个 package.json 都是 LF）、Winfinity 相关未提交文件、`bridge.test.ts`、

**教训**：在这台机器上不要用 `sed -i` 编辑 CRLF 文件，它会静默改写整个文件的换行符。

### 8.5 `maxPayload` 1MB → 8MB（我引入的误伤风险）

ws 超限时是以 **1009 直接关闭连接**，扩展随后重连，等于监控中断。
1MB 对"全量珠盘同步"这类负载余量偏薄。已提高到 8MB：
仍能把 ws 默认的 100MB 收回来，但不会因为正常负载误伤断言连接。
